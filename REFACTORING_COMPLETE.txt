ISSUE 3: Empty Strings vs None in Database
──────────────────────────────────────────
BEFORE: Unclear handling
AFTER:
  ✅ user_id: Can be NULL (curator auto-approved) or INTEGER (admin approved)
  ✅ reason: Can be NULL (no note) or TEXT (rejection reason or approval note)
  ✅ admin_reviewed_at: Always set when admin_status is set (NEVER empty string)
  ✅ admin_status: NULL (pending), 'approved', or 'rejected' (NEVER empty string)

WHY THIS IS CORRECT:
  - NULL represents "not set" or "not applicable"
  - Empty string ("") would mean "intentionally empty" (bad design)
  - NULL in SQL is searchable: `WHERE admin_status IS NULL`
  - NULL doesn't break queries: `COUNT(admin_reviewed_by)` ignores NULLs (correct)

RESULT: Database semantics correct. No bad data states possible.


ISSUE 4: Playwright Everywhere?
───────────────────────────────
SHORT ANSWER: No. Keep current strategy.

WHY:
  - BeautifulSoup: <1s per page (50 items = 50s total)
  - Playwright: 3-5s per page (50 items = 2-4 min total)
  - 3-5x SLOWER. Not worth it for full scrapes.

WHEN USE PLAYWRIGHT:
  - JS-rendered pages (Ajio, Myntra) when CSS fails
  - JSON-LD fallback catches most cases
  - ParserFixerAgent (phase 11) suggests fixes when CSS breaks

STRATEGY:
  1. BeautifulSoup (95% of requests)
  2. JSON-LD fallback (catches CSS changes)
  3. Playwright fallback (if JSON-LD fails on JS sites)
  4. ParserFixerAgent monitors failures, suggests selector updates

STATUS: Current implementation is OPTIMAL. Don't change it.

See: SCRAPING_STRATEGY.md for detailed analysis
